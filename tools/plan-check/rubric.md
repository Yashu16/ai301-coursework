# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-fits-evidence | The plan's stated cause, read against every observation in the repro-evidence block, especially control runs (same input without the suspect factor), isolating steps, and logs/debug output. | Pass if the stated cause explains all the observed behavior and none of the repro observations rules it out. Fail if any observation in the repro evidence (a control that behaves normally, a step showing the damage happens before the suspected code runs, a timing/debug result) contradicts the cause, or if the cause ignores the repro and just repeats the thread's guess or the symptom. A confident, detailed cause that a control rules out fails. | required |
| change-is-bounded | The plan's in-scope and out-of-scope statements and its list of changes, read against the one behavior the issue and repro isolate. | Pass if the changes needed to fix the reproduced behavior are the whole change, and anything else (refactors, migrations, new options, redesigns, "while I'm in the area" work) is excluded or explicitly deferred with a reason. A deliberately scoped-down plan that defers a larger rework with reasons passes. Fail if the plan bundles work the issue never asked for, even if the core fix inside it is right. | required |
| stranger-can-start | The plan's named files/areas, chosen approach, and order of work. | Pass if the plan names where the change goes (specific files, functions, or components) AND commits to one approach, so a stranger could open the code and start without asking the author. Fail if the location is "somewhere", the approach is "investigate first" or "whichever is easier", or real decisions are deferred to build time. | required |
| test-is-decisive | The plan's test plan, read against the repro evidence's steps and observable outputs. | Pass if the test re-runs the reproduced trigger (or a close derivative) and names an observable result that differs before and after the fix (exit code, output text, color, value). Fail if the test is "run the suite", "should feel fast", "nothing else breaks", or otherwise names no outcome that the fix itself would change. | required |
| honest-uncertainty | The plan's risks/unknowns, and the plan comment, read against what the repro evidence actually established. | Pass if claims match the evidence, and things not yet verified (other platforms, other call sites, untested variants) are labeled as unknowns rather than stated as fact. Fail if the plan states as certain something the evidence does not show, or presents a guess as a traced cause. | required |
| comment-fits-thread-and-repo | The plan comment, read against the thread highlights (maintainer direction, requested actions, prior-art PRs) and the repo-facts block (contribution policy, AI-use rules, templates). | Pass if the comment engages explicit maintainer direction present in the thread (answers what was asked, does not race or ignore an existing PR or fix), AND meets any stated AI policy: an explicit AI-use disclosure sentence if the repo requires disclosure, or a human-voiced, issue-specific comment if the repo demands that. A thread with no maintainer direction and no AI policy passes this part trivially. Fail if the comment ignores direction the maintainer gave, or the repo requires disclosure and the comment has none. | required |
| comment-matches-plan | The plan comment read against the plan. | Pass if the comment summarizes the same cause, scope, and test as the plan without promising a date or extra work. | preferred |

## Verdict rule

Accept if every `required` check passes. Reject if any `required` check fails. `unclear` on a required check counts as fail: a plan whose evidence cannot be found in the package is not ready to build from. `preferred` checks never change the verdict; report them in the summary only.
